### 2 RAG与知识库 技术栈

关系数据库选用PostgreSQL 

该项目的后端中允许用户自行上传有关文件，并作为知识库，

**pgvector**+llama_index，做最小MVP，能够切实正确运行起来才是最合适的。

实体关系存储选用



邮件场景必须做**混合检索**

```plain
用户提问 → 查询理解(改写/扩展) 
    → 并行检索：向量检索(语义) + BM25关键词检索
    → 结果融合(RRF重排序)
    → 重排序模型(reranker)
    → Top-K片段 → LLM生成
```

**邮件场景的特殊处理：**

+ **元数据过滤**：检索时先按 `发件人`、`时间范围`、`邮件标签` 过滤，再做语义检索
+ **会话感知**：同一主题邮件串（Thread）要作为整体chunk，避免割裂上下文
+ **附件处理**：PDF/Word附件单独解析入库，检索时关联到原邮件

**PostgreSQL 的 `nodes` + `edges` 表（或 JSONB 存属性）**，和下面的业务库共用，零额外组件

使用下面三张表进行模拟，而不是使用原生的neo4j进行存储

例如可以使用三张表模拟图谱：`entities`、`relations`、`entity_relations`。足够应付2-3用户的万级关系，且与持久化层统一

（这里只是举例子，实际以开发时为准）



###  邮件处理关键点

+ **分块策略**：按邮件 thread（会话）分块，而不是单封
+ **元数据强依赖**：vector payload 中必须包含： `sender`, `receiver`, `date`, `thread_id`, `labels`
+ **时间感知检索**：`date >= '2026-01-01'` 这类过滤非常常见

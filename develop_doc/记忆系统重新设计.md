基于 DeepMail 的业务特性（邮件场景、多 Agent 协作、长上下文、用户画像学习），我对记忆系统做了重新分层设计。核心思路是：**按"时间衰减 + 语义密度 + 调用频率"三维建模**，把原来的 4 层扩展为 6 层，并明确每层的存储介质、检索策略和生命周期。

---

## 重新设计的记忆层次架构

```
┌─────────────────────────────────────────────────────────────────────────────┐
│  L0: 瞬时记忆 (Ephemeral Memory) — 毫秒级                                   │
│  ─────────────────────────────────────                                      │
│  内容：单次 LLM 推理的临时上下文、工具调用中间结果、流式输出缓冲              │
│  载体：Python 内存 / asyncio ContextVar                                     │
│  检索：直接对象引用，无检索开销                                               │
│  销毁：推理结束立即释放，不落地                                               │
│  容量：~4K-16K tokens（单轮推理窗口）                                        │
└─────────────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  L1: 会话记忆 (Session Memory) — 分钟~小时级                                │
│  ─────────────────────────────────────                                      │
│  内容：当前 thread 的最近 N 轮对话、当前邮件草稿、用户正在写的邮件原文        │
│  载体：Redis / 内存 LRU Cache（Checkpointer 的快照缓存）                    │
│  检索：thread_id 直接加载，O(1)                                             │
│  淘汰：滑动窗口（最近 10 轮 或 32K tokens），超窗后触发摘要提炼               │
│  特殊：写邮件时，自动将草稿内容注入 assistant 上下文                         │
└─────────────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  L2: 话题记忆 (Topic Memory) — 天级 (1~7 天)                                │
│  ─────────────────────────────────────                                      │
│  内容：同一话题下的邮件簇摘要、对话摘要、待办关联（如"装修讨论"、"审稿周期"） │
│  载体：PostgreSQL + pgvector（按 topic_id 聚类）                            │
│  检索：向量相似度 + 时间衰减权重（越近越高） + topic 聚类约束                 │
│  生成：L1 超窗时，由 Summary Agent 自动提炼为话题摘要                         │
│  关联：与邮件 thread 双向链接，点击话题可回溯原始邮件                         │
└─────────────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  L3: 事件记忆 (Event Memory) — 周级 (7~90 天)                               │
│  ─────────────────────────────────────                                      │
│  内容：完整事件脉络（如"求职流程-某公司"、"项目交付-某客户"）                │
│        包含：时间线、关键决策点、待办完成状态、相关联系人                     │
│  载体：PostgreSQL 结构化表（事件表 + 时间线表）+ 向量摘要索引                 │
│  检索：结构化查询（时间范围、事件类型、联系人）+ 向量语义检索                 │
│  生成：L2 话题达到 3 个以上相关话题时，由 Event Agent 合并升级为事件          │
│  可视化：用户可在"重点事件看板"直接查看和管理                                │
└─────────────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  L4: 语义记忆 (Semantic Memory) — 年级 (永久，但可衰减)                     │
│  ─────────────────────────────────────                                      │
│  内容：用户画像、联系人关系网、事实知识、程序性偏好、工作流习惯               │
│  子类：                                                                      │
│    ├─ 画像层：职业、性格标签、沟通风格（正式/随意）、回复时效偏好             │
│    ├─ 事实层：重要决策记录、合同关键条款、项目里程碑（置信度+来源追溯）       │
│    ├─ 关系层：联系人图谱（实体-关系-实体，PostgreSQL 关系表模拟图）          │
│    └─ 程序层：用户专属工作流（如"收到审稿意见→3天内回复→生成待办"）          │
│  载体：PostgreSQL（结构化字段 JSONB）+ pgvector（语义向量）                  │
│  检索：混合检索（结构化过滤 + 向量语义 + 图遍历 2-hop）                      │
│  更新：LLM 抽取 (主,谓,宾,置信度,来源) → 冲突消解 → 写库                     │
│  衰减：低频事实置信度逐年衰减，低于阈值进入"冷存储"                          │
└─────────────────────────────────────────────────────────────────────────────┘
                                    │
                                    ▼
┌─────────────────────────────────────────────────────────────────────────────┐
│  L5: 外部记忆 (External Memory) — 按需加载                                   │
│  ─────────────────────────────────────                                      │
│  内容：用户上传的知识库文档、邮件附件中的关键文档、RAG 索引                   │
│  载体：专用向量库（可独立部署，与 L4 隔离）+ 文档元数据表                     │
│  分区：用户自定义分组（合同库、产品资料库、个人笔记库...）                    │
│  检索：query 改写 → 多路召回（BM25 + 向量 + 元数据过滤）→ 重排序 → 引用溯源  │
│  特点：不参与记忆衰减，只随文档增删更新；检索结果带引用块，可点击溯源         │
└─────────────────────────────────────────────────────────────────────────────┘
```

## 记忆流转与升级机制

```
新邮件/对话进入
    │
    ▼
┌─────────────┐     超窗/会话结束      ┌─────────────┐
│   L1 会话    │ ────────────────────→ │   L2 话题    │
│  (原始上下文)│   Summary Agent 提炼   │  (天级摘要)  │
└─────────────┘                       └─────────────┘
                                              │
                          3+ 相关话题聚类      ▼
                    ┌─────────────────────────────────┐
                    │         L3 事件                  │
                    │   (周级，完整事件脉络)            │
                    │   如："求职流程-字节跳动"         │
                    └─────────────────────────────────┘
                                              │
                          事件沉淀/人格提取    ▼
                    ┌─────────────────────────────────┐
                    │         L4 语义                  │
                    │   (年级，用户画像与事实)          │
                    │   如："用户是产品经理，偏好正式语气"│
                    └─────────────────────────────────┘
```

## 每层的关键设计决策

| 层级 | 核心设计决策 | 为什么这样设计 |
|------|-------------|---------------|
| **L0 瞬时** | 不落地、纯内存 | 避免 I/O 阻塞 LLM 推理，工具调用结果用完即抛 |
| **L1 会话** | 滑动窗口 + 草稿注入 | 写邮件场景必须让 AI 看到用户正在输入的草稿 |
| **L2 话题** | 按 topic 聚类，而非时间切片 | 邮件天然按 thread/topic 组织，同话题邮件可能跨数天 |
| **L3 事件** | 结构化时间线 + 状态机 | 重点事件看板需要展示"进度"，必须有时间线和状态 |
| **L4 语义** | 结构化+向量双轨 + 置信度 | 用户画像需要精确查询（如"用户的老板是谁"），事实需要语义模糊匹配 |
| **L5 外部** | 独立分区、检索即引用 | 知识库内容必须可溯源，且不能与用户内生记忆混淆 |

## 记忆检索的优先级策略（Prompt 组装时）

当用户提问时，按以下优先级组装上下文（每层有预算上限，总预算受长上下文压缩控制）：

```python
context_budget = {
    "L1_session":   0.30,  # 当前会话最优先，占 30%
    "L2_topic":     0.20,  # 近期相关话题，占 20%
    "L3_event":     0.15,  # 相关事件脉络，占 15%
    "L4_semantic":  0.20,  # 用户画像+事实+关系，占 20%
    "L5_external":  0.15,  # RAG 知识库，占 15%
}
```

**压缩策略**：如果总 tokens 超过模型上下文上限：
1. 先压缩 L5（只保留高相关性 chunk）
2. 再压缩 L3（只保留事件摘要，丢弃时间线细节）
3. 再压缩 L2（只保留最近 1 个相关话题）
4. L1 和 L4 最后压缩（L1 保留最近 3 轮，L4 保留最高置信度事实）

## 记忆写入与冲突消解（L4 语义记忆）

```
输入：新邮件 / 对话记录
    │
    ▼
LLM 抽取结构化三元组 + 置信度
    │
    ├── 实体链接（向量相似度 > 0.85 视为同一实体）
    │
    ├── 冲突检测
    │     ├─ 同一实体新关系 vs 旧关系 → 时间戳覆盖 + 置信度加权
    │     ├─ 矛盾事实（"是学生" vs "是老师"）→ 置信度高覆盖低，同置信度取最新
    │     └─ 无冲突 → 直接写入
    │
    └── 写入 L4（结构化表 + 向量索引）
```

## 与原有设计的对比改进

| 原设计 | 新设计 | 改进点 |
|--------|--------|--------|
| 4 层（工作/短期/中期/长期） | 6 层（增加 L0 瞬时、L3 事件、L5 外部独立） | 更精细，L3 事件直接支撑"重点事件看板"业务 |
| 中期记忆按时间归档 | L2 按 topic 聚类 | 更符合邮件 thread 的业务形态 |
| 长期记忆统一存储 | L4 分画像/事实/关系/程序四个子类 | 检索策略不同，结构化查询 vs 向量检索分离 |
| RAG 与记忆混为一谈 | L5 外部记忆独立分层 | 明确区分"用户内生记忆"和"外部知识库" |
| 记忆衰减仅提概念 | 每层有明确衰减公式和冷存储机制 | 可工程落地，防止记忆膨胀 |

# 项目定位一句话

这是一个AI agent项目。我给他取名为DeepMail，下面是对这个项目的一个大概介绍。

AI辅助的邮箱助手（能够登录（多用户隔离）），能够进行AI辅助邮箱管理（邮件查收、邮件自动分类、垃圾广告邮件过滤、重要信息提取与总结、待办事项管理、辅助邮件回复等功能，这里的功能不是全部，详细功能主业务功能 中查看），可以直接与agent进行对话来完成有关的任务（比如邮件查询、人物检索、）并且背后是一个邮件助手管家，能够记录和学习到用户的人格与背景画像，基于学习到的知识背景来完成邮件回复草稿的生成。另外支持外部导入支持库，例如：客户询问关于某个合同的情况，能够利用RAG功能检索到有关的内容。

agent层面：支持多agent的协作，工具调用，skill（包括自进化的skill功能）、agent记忆等，支持向量化记忆检索。

RAG知识库：能够自定义用户导入知识库（按照分组或者知识库1,2,3，用户可以自行取名），用于模型回答用户问题的回答。

## 2助手辅助写邮件功能

除了用户能够自行书写以外，还可以用户点击AI辅助书写，旁边展示出于与AI的聊天框，随时在书写过程中进行AI介入，AI书写完成后，将结果填充到草稿中，用户可以自行修改草稿，并人工操作发送。（在写邮件过程中，会将当前邮件的内容注入到上下文，用户向助手提问的话，助手能够看到用户的草稿），当然agent需要去记忆中进行检索，重要的内容需要agent进行检索，比如提到了某个品牌策划案，就需要检索与品牌策划案有关的信息（如果外部知识库上传了这个信息，需要RAG检索），以及与该用户最近的邮件往来都是比较重要的信息来源。

## 3 邮件摘要等信息

包括邮件摘要、重要事项、待办事项等信息的抽取，能够直观总结给用户查看，同时关键和有意义的信息也是重要的数据来源，会作为agent的记忆。

将已经完成这一步的邮件的摘要等信息能够存储下来，不能每次都请求AI，新收到的邮件能够自动执行这一步。

实体关系（利用关系型数据库模拟图数据库来存储），当收到新邮件后，agent自动进行关系构建。

这些重要信息能够持久化为记忆（值得记忆的，广告等不作为记忆的点，具体看agent设计中的记忆）



关系信息抽取**自动构建流程：**

1. 新邮件到达 /历史→ LLM提取实体和关系（使用结构化输出/Function Calling）
2. 与已有实体做实体链接（向量相似度匹配，阈值0.85以上视为同一实体）
3. 写入数据库中进行持久化
4. 冲突处理：同一对实体的新关系与旧关系合并或更新



## 4.待办事项管理

待办事项会独立存储，能够在待办事项栏目看到，分别特定日期完成事项（如开会）、特定截止日期事项（如：在几月几号之前提交报告）、无特定日期事项（如：大扫除），能够根据事项链接点击到特定的邮件。

对于有明确时间的，能够在日历导视图中看到。

支持对特定类型的待办事件进行合并归类



## 5.邮件自动分类功能

对邮件根据分类邮件箱的内容，进行邮件分类，对于修改了邮箱的框架的话，要进行重新分类

用户自定义的分类箱要让用户填写一段描述的话，用于辅助ai进行合理的分类，更好的了解用户的意图。



## 6.邮件打标功能

自动对特定邮件进行标签打标（默认不点击重新打标，不会更改已经打标的邮件，新邮件自动打标后经过用户确认，将打标结果存储下来（也就是系统给出默认的打标））

例如：可以自定义设置账单、

## 7. 与助手的聊天功能

可以直接与助手进行聊天，助手调用工具完成特定任务，比如让助手总结昨天收到的全部邮件。在收件箱的地方，打开特定邮件后，可以点击邮件上面的发送到到DeepMail助手的聊天里面，聊天框下面能够看到已经选中的邮件，与助手直接聊天的时候能够不需要说明针对哪个邮箱。同样，加入让助手回复某个邮件以后，还可以默认生出，是否进入到”写信“页面（此时会将草稿带入到页面中）。

## 8 当前N天内重点事件看板（默认30天）

能够设置重点事件看板（具有延续性+进展性+持续性+短期活动性的事情），比如找工作投简历、期刊审稿意见、某个比赛的官方热线邮箱，例如：可以将移动杯作文大赛的所有投稿，列入到终点时间看板中（可以设置结束时间、也可以手动设置），能够展示重点事件的邮件条数，总结进度，自动将新收到的邮件加入其中，重点进度回顾。

## 1.记忆与存储检索设计

具体的分层记忆与存储为：

┌─────────────────────────────────────────────────────────────┐
│  第一层：工作记忆 (Working Memory)                            									  │
│  ─────────────────────────────────────               						       │
│  存储内容：当前推理的中间状态、工具调用结果、临时变量              							│
│  生命周期：秒级~分钟级，任务结束即销毁                       									   │
│  存储位置：Python内存 					  									         │
│  检索方式：直接状态访问                                     										   │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  第二层：短期记忆 (Short-Term Memory / 会话记忆)            							    │
│  ─────────────────────────────────────               					       │
│  存储内容：当前会话的最近N轮对话、当前处理的邮件上下文    						         │
│  生命周期：单次会话内（分钟~小时级）                       									     │
│  存储位置：Checkpointer (PostgreSQL)             										    │
│  检索方式：thread_id直接加载                                										   │
│  容量：最近N轮对话 或  N K tokens（滑动窗口）               								     │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  第三层：中期记忆 (Episodic Memory / 话题记忆)                  							│
│  ─────────────────────────────────────                  						    │
│  存储内容：近期话题的摘要（如"装修讨论"、"论文审稿"、"学生申请"） 						 │
│  生命周期：7~30天，过期后自动归档提炼                     									 │
│  存储位置：PostgreSQL + 向量检索                           										    │
│  检索方式：向量相似度检索 + 时间衰减排序               									          │
└─────────────────────────────────────────────────────────────┘
                              │
                              ▼
┌─────────────────────────────────────────────────────────────┐
│  第四层：长期记忆 (Semantic Memory / 语义记忆)              									    │
│  ─────────────────────────────────────               						       │
│  存储内容：用户画像、偏好习惯、重要事实、联系人关系网       							       │
│  生命周期：永久（除非手动删除）                               										  │
│  存储位置：PostgreSQL结构化表 + 向量数据库                    								   │
│  检索方式：结构化查询 + 向量语义检索                     									        │
│  子分类：                                                  													  │
│    ├─ 用户画像记忆：职业、性格、沟通风格                 									        │
│    ├─ 事实记忆：重要事件、决策记录                            										   │
│    ├─ 关系记忆：联系人图谱（存储在知识图谱层）     								               │
│    └─ 程序记忆：Agent学到的用户专属工作流                      								   │
└─────────────────────────────────────────────────────────────┘

"用户画像+事实"存储。设计为**结构化+向量化双轨存储**，关键字段可使用JSONB存储，用户画像表（结构化，精确查询）

事实记忆表（向量化，语义检索）

```plain
用户提问
  ├── 1. 短期记忆：加载当前会话上下文（Checkpointer）
  ├── 2. 中期记忆：向量检索近期相关话题（pgvector/PostgreSQL）
  ├── 3. 长期记忆：
  │     ├── 3a. 用户画像：结构化查询（PostgreSQL）
  │     ├── 3b. 语义记忆：向量检索（PostgreSQL pgvector）
  │     └── 3c. 关系网络：图查询（PostgreSQL关系表（不使用重量级别的neo4j））
  └── 4. 外部知识库：RAG检索（邮件+文档）
  
→ 合并所有上下文 → 构造Prompt → LLM生成
```

## 该项目的设计原则

1.开发阶段要考虑到agent的后期评测和trace的可追溯性以及方便定位agent的问题。可以考入引入地方库方便进行评测。

2.需要考虑长上下文情况下的压缩问题。

3.工具调用、LLM调用、记忆等要考虑到harness工程的思想，要防止死循环、中途出错、超上下文，记忆的事实冲突、出错的兜底机制等生产环境项目应该考虑的必要工程性的内容。

## 0. 一句话定位

**DeepMail = 多 Agent 协作 + 6 层记忆 + 人格画像 + RAG + Vue 3 前端的个人邮箱 AI 助手。**
后端 LangGraph 编排 5 个 ReAct sub-agent 自主调度；前端 Vue 3 + Naive UI 提供完整可视化。

## 3. Agent 实现逻辑（LangGraph）

### 3.1 主图结构

```
START → supervisor → [conditional dispatch] → {email, todo, draft, rag, tidy}（并行，最多 3 个）
                                              ↓
                                          aggregator → END
```

源码：`backend/app/agents/graph.py:64-71`

### 3.2 Supervisor 节点

文件：`backend/app/agents/supervisor.py`

**职责**：LLM 读取用户 query，输出 JSON 路由决策。

**Prompt 关键约束**：
```text
- 只能选 1~3 个 agent（避免并行风暴）
- 多领域 → 并行；强依赖 → 让子 agent 内部调工具
- 输出**只**含 JSON 对象（不加 ```、不加说明）
格式：{"agents": ["email", "todo"], "reasoning": "..."}
```

**Pydantic Schema**（`RoutingDecision`，含 `description`）：
```python
class RoutingDecision(BaseModel):
    agents: list[Literal["email","todo","draft","rag","tidy"]] = Field(
        min_length=1, max_length=3
    )
    reasoning: str = ""
```

**关键实现细节**：
- **不用** `with_structured_output`（OpenAI SDK 解析 ```json fence 会失败）→ 改用 `llm.ainvoke()` 手动解析
- `_strip_markdown_fence()` 兼容多种格式
- 解析失败兜底 `RoutingDecision(agents=["email"])` 不让主流程崩
- `{QUERY_PLACEHOLDER}` 用 `.replace()` 而非 `.format()`（避免 `{"agents": ...}` 被当成 format 占位符）

**dispatch 限制**：即使 LLM 给了 5 个 agent，也截断到 `agents[:3]`，并行上限 3。

### 3.3 5 个 ReAct Sub-Agent

文件：`backend/app/agents/sub_agents.py`

每个 agent 用 `langgraph.prebuilt.create_react_agent()` 构造，绑定专属 tools：

| Agent | 工具 | 用途 |
|---|---|---|
| **email** | `list_emails` / `get_email` / `summarize_email` / `classify_email` | 查收 / 摘要 / 分类 |
| **todo** | `list_todos` / `create_todo` / `list_emails` | 待办管理 |
| **draft** | `draft_reply` / `get_email` / `list_emails` | 起草回复 |
| **rag** | `search_knowledge` | 知识库检索 |
| **tidy** | `list_emails` / `classify_email` / `get_email` | 批量整理 |

**关键防死循环**：Mock LLM 用 `_tool_call_count` 计数：
- 第 1 次：返回 `tool_call`
- 第 2 次：返回 `stop`
→ 保证 ReAct 最多跑 2 轮就停（真实 LLM 凭模型自觉）

### 3.4 Aggregator 节点

文件：`backend/app/agents/aggregator.py`

汇总逻辑：
1. 从 `state["messages"]` 提取最近 5 条 `AIMessage`（各 sub-agent 的输出）
2. 用 LLM 二次生成 → 面向用户的简洁最终回复
3. 把最终回复再 push 一条 AIMessage 到 messages（保留 history）

**Aggregator Prompt** 规则：直接给用户结论、不要列"agent A 说..."、保留关键数据、中文输出、合并 errors。

### 3.5 Tools 实现（共 10+ 个）

`backend/app/agents/tools/` 下：
- `email_tools.py` — list / get / summarize / classify
- `todo_tools.py` — list / create
- `draft_tools.py` — draft_reply（带 persona + 联系人历史 + 语言对齐）
- `rag_tools.py` — search_knowledge
- `context.py` — `agent_context()` asynccontextmanager（注入 trace_id/span_id）

每个 tool 是 `@tool` 装饰的 LangChain Function，自动生成 schema。

### 3.6 GraphState

文件：`backend/app/agents/state.py`

```python
class GraphState(TypedDict, total=False):
    user_id: str
    session_id: str
    trace_id: str
    current_time: str          # "2026-08-04 10:30 星期二"

```

### 3.7 Build / 缓存

`graph.py:build_graph()` 按 `(user_id, session_id)` 缓存编译好的图（`_graphs: dict`）。
切用户/会话才重建；同会话第二次请求复用。

## 4. 上下文工程（Context Engineering）

### 4.1 设计目标

让 LLM 看到**刚好够用**的上下文，不超 token 预算、不漏关键信息。

### 4.2 当前实现（v2-M1 后）

#### Token 计数（v2-M1 升级）

文件：`backend/app/agents/tokenizer.py`

```python
@lru_cache(maxsize=1)
def get_tokenizer():
    return tiktoken.get_encoding("cl100k_base")

def count_tokens(text: str) -> int       # 纯文本
def count_message_tokens(msg) -> int     # 计入 content + tool_calls + reasoning_details
def count_history_tokens(messages) -> int
def truncate_to_tokens(text, max_tokens) -> str
```

**为什么 `cl100k_base`**：GPT-4 / GPT-3.5 通用 BPE；MiniMax-M3 是 MiniMax 自定义模型无对应映射，`cl100k_base` 是误差最小的折中（±10%）。

#### 多轮摘要触发

文件：`backend/app/agents/context_builder.py:179-209`

```python
def should_compress_session(
    history_msgs: list,
    *,
    trigger_tokens: int | None = None,
    trigger_chars: int | None = None,   # 兼容旧路径
    keep_recent: int = 4,
) -> bool:
    # 1. 消息数 > keep_recent + 2
    # 2. 总 token 数 > trigger_tokens  （v2-M1 用 count_history_tokens）
```

## 5. 记忆系统实现

### 5.1 6 层架构（设计文档定义，当前实现覆盖 L0/L1/L2/L3/L4，L5 部分）

```
L0 瞬时     ─ 进程内存（GraphState）── 当前请求
   ↓
L1 会话     ─ PostgreSQL chat_messages ─ 最近 10 轮 / 压缩摘要
   ↓ (超 token 预算)
L2 话题     ─ PostgreSQL memory_medium_topics + pgvector ─ 每轮对话提炼 1-3 topic
   ↓ (≥ 3 个相关 topic 聚类)
L3 事件     ─ PostgreSQL memory_events + memory_event_timeline ─ 手动触发聚合
   ↓
L4 语义     ─ PostgreSQL memory_long_term (key-value JSONB) + 衰减公式
   ↓
L5 外部     ─ PostgreSQL knowledge_chunks (vector+BM25+RRF+rerank) ─ 用户上传/邮件索引
```

### 5.6 L4 语义记忆（长期事实 + 衰减）

**载体**：`memory_long_term`（key-value JSONB）

**字段**：
```sql
CREATE TABLE memory_long_term (
  id UUID PRIMARY KEY,
  user_id UUID NOT NULL,
  key VARCHAR(128),
  value JSONB,
  importance FLOAT,
  decay_score FLOAT,
  category VARCHAR(32),     -- profile / fact / preference / misc（v3 真正使用）
  updated_at TIMESTAMPTZ,
  UNIQUE(user_id, key)
);
```

**衰减公式**（`backend/app/memory/long_term.py:30-43`）：

```python
decay_score = importance * exp(-λ * days_since_update)
DEFAULT_DECAY_LAMBDA = 0.01   # λ
DEFAULT_MIN_DECAY = 0.1       # 查询过滤阈值
```

举例：
- importance=1.0, days=0 → score=1.0
- importance=1.0, days=100 → score=exp(-1)≈0.368
- importance=0.5, days=300 → score≈0.5×exp(-3)≈0.025（被过滤）

**CRUD**：
- `upsert_long_term()`：同 (user_id, key) 存在则更新 + 重置 decay_score
- `list_long_term(min_decay=0.1)`：按 decay_score 降序
- `delete_long_term(key)`
- `run_decay_update(user_id)`：手动刷新所有行的 decay_score

**自动提炼**（`extract_long_term_from_conversation`）：
- LLM 输出 `[{"key", "value", "importance", "category"}]`
- 失败 / mock 模式跳过
- 当前**未在 chat fire-and-forget 中调用**（M4 接）
